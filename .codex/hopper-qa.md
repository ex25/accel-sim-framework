# Hopper PTX 技术问答

这里保存规划讨论中的技术问题与解释。当前代码的调查结论见[调查依据](hopper-notes.md)；后续实现可能出错的场景及处理要求放在[实施计划的对应阶段](hopper-plan.md#stages)，测试方法见[验证方案](hopper-validation.md)。

## 转换、路由、重排分别是什么

```text
输入 → 类型转换 → 路由打分、选专家 → 按专家重排 token
     → 每个专家的 FC1 / SwiGLU / FC2 → 逆重排、按路由权重合并 → 输出
```

- **转换**：把输入或路由权重换成内核需要的数据表示，例如 BF16 与 FP32 之间的转换。
- **路由**：门控矩阵乘法计算每个 token 对各专家的分数，再用 top-k 等步骤选择专家和对应权重。
- **重排**：把交给同一专家的 token 放在一起，供专家矩阵乘法成批处理。一个 token 选中多个专家，就会进入多个专家组；最后按映射恢复原 token 顺序并加权合并。

实现时，转换、top-k、计数/重排代表内核可在[阶段 1](hopper-plan.md#stage-1)先测；门控 GEMM 需要[阶段 2](hopper-plan.md#stage-2)的普通异步拷贝。这里说的是开发测试顺序，完整前向仍按上面的数据流程执行。

## 两条分支是实施计划还是运行时分支

是开发和验证工作的两条依赖线：

| 开发工作 | 提供什么 | 实施位置 |
| --- | --- | --- |
| 线程块协作与搬运 | cluster/DSMEM、屏障、tensor map、TMA 输入和写回 | 阶段 3～5 |
| 矩阵计算与寄存器 | 矩阵布局、64 项结果传递、寄存器配额与异步 WGMMA | 阶段 6 |

两条线可以分别做小测试；非组播 TMA 输入、mbarrier 和单次 WGMMA 分别通过后，立即做[首次联测](validation/stage-5.md#early-integration)，不用等两条线全做完。阶段 7 再集成真实专家和完整前向。不要求两个人同时开发或创建两个 Git 分支。实际运行时，同一个专家 GEMM 同时使用搬运和计算能力，并允许两者在安全的时段重叠。

## “多模块、默认名称和共享符号表”到底是什么意思

**这里的模块是一份编译得到的 GPU 代码，不是 MoE 的一个专家，也不是一层网络。** 当前冻结材料里，每份 PTX 文件包含一个可启动的内核入口，称为 entry。主机程序先登记这些代码，随后按需要调用入口。

举三个当前项目里的例子：

| 模块 | 里面的代码做什么 | 调用关系 |
| --- | --- | --- |
| 模块 0 | 输入类型转换 | 前向准备输入时调用 |
| 模块 2 | Mixtral/128 的 gating GEMM，计算路由分数 | 适用于这个冻结尺寸的打分调用 |
| 模块 16 | 专家矩阵乘法 | 九例都用它，每次前向调用两次：FC1 和 FC2；同一代码通过不同参数计算不同矩阵 |

Triton 会按模型尺寸、token 数及编译选择生成不同版本，例如 Qwen64/128 的 gating 是模块 71。九例用到的不同版本去重后共有 **110 个模块**；每次前向实际只启动 22～24 次内核。110 不是专家数，也不是一次前向要计算 110 次。[完整模块表](../workloads/moe/docs/ptx-modules.md)

当前[启动器](../workloads/moe/source/launcher.cu)会先登记全部 110 份代码，再按某个用例的记录选择要调用的入口。可以把具体过程写成：

```text
登记模块0：转换入口 ───────┐
登记模块2：路由打分入口 ──┤
登记模块16：专家入口 ─────┼→ 按用例顺序选择入口并传参数
登记其余模块 ────────────┘     转换 → 打分 → … → FC1 → … → FC2
```

**默认名称**指模拟器在当前 CUDA 分支里把提取来源的名称统一记成 `default`。这不是把所有函数改成同一个名字：模块仍有注册 handle，函数仍有自己的 entry 名和主机调用标记。

**缓存**指已经解析过的代码信息会保存起来，后续注册可能复用，避免重复解析。要核查的是缓存按什么键查找、返回的内容是否包含当前所需入口；临时提取文件的名称/路径也只是代码找到正确内容的线索，不是丢模块的直接证据。

**符号表**是一张记录“这个名字对应哪个函数或变量”的表。当前 parser 会把多份 PTX 的名字放进共用表。例如解析 A 后有 `write_a`，再解析 B 后表里可能同时有 `write_a` 和 `write_b`。此时即便变量 `symtab` 在循环里每次都接收“刚解析返回的表”，最后拿到的仍可能是包含 A、B 的共用表，**不能只看循环最后一次赋值就断言 A 被丢掉了**。

真正要确认的是：登记 A、B 后，调用 A 能否找到 A 的函数和数据，调用 B 能否找到 B 的函数和数据，以及各自资源信息有没有混淆。最小测试很直观：

```text
模块A：write_a 写出自己的标记11
模块B：write_b 写出自己的标记22
登记A和B后调用 A → B → A
预期输出        11 → 22 → 11
```

标记使用独立名称，并让两模块带各自的 global/constant 数据和资源信息。若全部正确，就保留现有组织方式；若 A 找不到、拿到 B 的数据或资源，才沿注册/缓存/符号绑定定位并局部修正。**目前只有静态代码线索，没有这类错误的运行复现。** 测试及处理安排在[阶段 0 实现](plans/stage-0.md)和[阶段 0 验收](validation/stage-0.md)。

## CTA、SM、cluster、DSMEM 是什么

CTA 就是 CUDA 线程块；SM 是执行线程块的硬件单元；shared 是线程块使用的片上共享内存。cluster 是一组协作的 CTA，rank 是 CTA 在这组中的编号。DSMEM 让同一个 cluster 内的 CTA 能定位和访问另一 CTA 的 shared。

当前专家 GEMM 的 cluster 为 `1×2×1`，包含两个 CTA。每个 CTA 的 shared 都是独立对象，目标 CTA 身份与 shared 内偏移共同确定访问位置。模拟器要实现的映射和调度见[阶段 3](hopper-plan.md#stage-3)。

## 真实 GPU 是否限制每个 SM 只能驻留一个 CTA

没有这种一般性限制，能驻留几个取决于该内核的 shared、寄存器、线程数等资源用量。

当前专家内核每个 CTA 申请 215040 字节动态 shared，当前 H100 配置每 SM 有 233472 字节。两个 CTA 仅动态部分就需 430080 字节，超过单 SM 容量，因此这两个 CTA 必须跨 SM 驻留。H100 记录的每 CTA 总分配为 216064 字节，其中驱动保留 1024 字节、PTX 静态部分为 0；驱动保留量不能当成 PTX 静态声明。[资源证据](hopper-notes.md#resource-facts)

## 要补的主机函数各有什么用

| 接口 | 在当前启动器中的用途 | 实施位置 |
| --- | --- | --- |
| `cudaGetDriverEntryPointByVersion` | 获取 `cuTensorMapEncodeTiled` 的函数入口 | 阶段 5 |
| `cuTensorMapEncodeTiled` | 把地址、形状、步长等编码为 TMA 使用的 128 字节描述符 | 阶段 5 |
| `cudaFuncSetAttribute` | 设置函数允许使用的大动态 shared 上限 | 阶段 0 |
| `cudaLaunchKernelExC` | 按本次 grid、block、动态 shared 和 cluster 属性启动专家内核 | 阶段 3 |
| `cudaLaunchKernel` | 启动普通内核，也传入本次动态 shared 数量 | 阶段 0 |

`cudaFuncSetAttribute` 设置的是许可上限，实际分配量由每次 launch 参数决定。当前已经查到的接口和传递缺口见[当前代码事实](hopper-notes.md#current-gaps)。

tensor map 已决定使用模拟器自己的内部表示，主机编码、PTX 复制/修改与 TMA 共用同一份语义；不要求与真实 GPU 的不透明编码互换。[已确认决定](hopper-planning-decisions.md)

## “不能启动 cluster、错误分配 shared”现在具体指什么

已确认的是：扩展启动接口尚未导出，动态 shared 没有完整传到分配/占用链路，函数 opt-in 被忽略。这些是静态核查到的当前缺口。[源码依据](hopper-notes.md#current-gaps)

两个 CTA 被错误映射到同一个 shared 对象、调度后互等等，属于后续 cluster 实现需要检查的情形。具体例子集中在[阶段 3](hopper-plan.md#stage-3)，不列为当前已经发生的故障。

## 为什么会读到旧 tile、提前复用 shared 或卡死

这些具体故障尚未在当前 PTX workload 上复现。tile 是矩阵的一块数据；shared 缓冲区会循环使用，异步指令发起后数据传输仍可能继续。程序通过等待指令决定何时可以读取或覆盖缓冲区。

因此，等待是否通过必须由实际完成状态决定。“发起”“源已读完”“结果可用”“目标写入完成”各有用途，不能混为一件事。具体时间顺序和可能出错的例子放在所属阶段：

- [阶段 2](hopper-plan.md#stage-2)：普通异步拷贝的数据可消费条件。
- [阶段 3](hopper-plan.md#stage-3)：两个 CTA 的存储身份与共同推进。
- [阶段 4](hopper-plan.md#stage-4)：屏障的对象、到达、字节计数和阶段。
- [阶段 5](hopper-plan.md#stage-5)：TMA 旧 tile 与写回前覆盖缓冲区的例子。
- [阶段 6](hopper-plan.md#stage-6)：WGMMA 结果等待与搬运/计算重叠。

这些要求随对应能力实现；不需要在开始 DSMEM 之前另做一次“修复未来故障”。单 CTA 异步拷贝也需要正确等待，因此旧 tile 和提前复用并不专属于 DSMEM。

## 64 项结果和寄存器 bank 分别要做到什么程度

当前 `m64n128k16` WGMMA 由 128 个线程协作，每线程持有 64 项 FP32 累加结果。现有部分寄存器表示只有 8/32 项容量，这是已经查到的缺口；解析、执行、依赖检查和写回都要扩展，属于[阶段 6](hopper-plan.md#stage-6)。

寄存器 bank 是寄存器存储的分组，端口决定每次能读写多少操作数。详细建模会影响寄存器访问等待，但当前先沿用已有 bank/端口模型，不新增复杂的物理重分配；保留 `setmaxnreg` 的 warpgroup 同步、配额增减和额度不足时等待。

64 项结果必须完整传递，WGMMA 必须保留异步语义，不能每次矩阵操作后强制等待。本机 256GB 内存可用于保存必要状态，同时记录实际用量、避免无用副本。这些均已确认，见[决定文档](hopper-planning-decisions.md)。
