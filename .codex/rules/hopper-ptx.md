# Hopper PTX 研究规则

## 目标边界

目标是把现有 Hopper SASS 时序模型所需的语义，逐步接入 PTX execution-driven
路径。第一版使用文本 PTX harness，优先覆盖 FlashAttention-3 前向所实际使用的
`sm_90a` 指令；完整 PyTorch/Triton 原生运行时是后续独立阶段。

H100 与 H200 共享 PTX 前端语义，使用各自的内存和配置参数。不能因为二者共享
指令集，就假设它们的容量、带宽、分区和时序完全相同。

## 证据规则

- 所有源码结论写出仓库、commit、相对路径、函数或符号。
- 区分“能被 lexer/parser 接受”、“有功能语义”、“有时序语义”和“有硬件验证”。
- SASS trace 是动态字段和时序路径的参考来源，不等于 PTX 功能正确性证明。
- A800 只用于同一数学问题的兼容实现对照，不使用固定倍率推算 H100/H200。
- 没有真实 Hopper 测量时，不写周期误差或硬件准确度结论。

## 实施规则

- 每个阶段必须先写目标、前置条件和预期结果，再修改代码。
- 每个阶段验收前，记录实际修改、命令、结果、失败日志和证据路径。
- 当前阶段不是 `已验收` 时，禁止开始下一阶段。
- 未实现的 Hopper opcode、modifier、地址语义或 API 必须默认严格失败并报告位置。
- 不用近似行为掩盖同步错误；只有显式记录的实验开关可以启用近似。
- 外层和内层 commit 必须成对记录。
- 不覆盖用户已有的 `experiments/` 或其他未相关修改。

## 文档规则

阶段文档面向人和后续模型，写清楚：为什么做、改哪里、数据怎样流动、如何运行、
预期是什么、实际是什么、怎样验收、失败后怎样停留。使用源码路径、函数名、伪代码
和短命令，不复制无法维护的大段源码。
