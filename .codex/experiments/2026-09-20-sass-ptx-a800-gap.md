# A800 SASS/PTX frontend gap experiment

Date: 2026-09-20
Evidence level: **Observed** for the local A800 software pipeline; **Needs hardware validation** for any A100/H100 absolute-performance interpretation.

## Objective and hypothesis

Measure how much Accel-Sim's trace-driven SASS path and execution-driven PTX
path differ when the same CUDA program is compiled for `sm_80`, executed on the
local A800, and simulated with the same `SM80_A100/gpgpusim.config` base. The
comparison is deliberately single-GPU and relative: it does not claim that an
A800 is an A100, and it does not model NVLink/NVSwitch/NVLS.

Hypothesis: the frontend choice will change dynamic instruction expansion and
IPC, while simple global-memory traffic should remain close. GEMV/GEMM cases
should show whether the gap grows with arithmetic intensity and problem size.

## Workloads

All workloads are deterministic FP32 CUDA kernels in the companion source and
verify a CPU checksum/max error. The matrix intentionally keeps simulator
runtime bounded:

| Family | Sizes |
|---|---|
| FMA chain | 1024 threads, 128 iterations |
| vector add | 4096 elements |
| strided global load | 4096 elements, stride 16 |
| shared reduction | 256 elements |
| branch divergence | 1024 threads, period 64 |
| atomic hotspot | 1024 threads, one counter |
| GEMV | 64, 128, 256 square matrices |
| GEMM | 16, 32, 64 square matrices |

## Reproduction

Raw outputs are intentionally outside git at
`/tmp/accelsim-sass-ptx-a800-20260920-v2/`.

1. Build and inspect the dual-code-object binary:

   ```bash
   make -C experiments/sass_ptx_gap clean all inspect
   ```

2. For each matrix row, execute the binary natively on A800 with NVBit
   injection (`SPINLOCK_HANDLING_MODE=0`, `ALLOW_REG_VAL_TRACING=0`,
   `TRACE_LINEINFO=0`), then run `post-traces-processing`.

3. Replay the processed trace matrix with `run_simulations.py -B SASS_PTX_GAP
   -C A100-SASS` and execute each generated `justrun.sh`.

4. Execute the same binary with `run_simulations.py -B SASS_PTX_GAP
   -C A100-PTX`. The generated `slurm.sim` wrapper was run directly, so its
   final shell status is 1 when it tries to move a nonexistent Slurm error
   file; every simulation itself emitted `GPGPU-Sim: *** exit detected ***`
   and `RESULT ... status=PASS`.

5. Collect the comparable counters:

   ```bash
   python3 experiments/sass_ptx_gap/collect_metrics.py \
     --sass-root /tmp/accelsim-sass-ptx-a800-20260920-v2/sass-runs \
     --ptx-root /tmp/accelsim-sass-ptx-a800-20260920-v2/ptx-runs \
     --trace-root /tmp/accelsim-sass-ptx-a800-20260920-v2/traces \
     --output /tmp/accelsim-sass-ptx-a800-20260920-v2/metrics.csv
   ```

## Results

`sim_cycle`, `sim_insn`, and `sim_ipc` are total simulator counters. Deltas
are `(PTX - SASS) / SASS`; they are not native CUDA event-time deltas.

All 12 native CUDA runs passed their checksum checks, all 12 A800 traces were
post-processed, all 12 SASS replays exited successfully, and all 12 PTX
simulations reached a passing functional result. PTX GEMV had a stable
−36.5% to −38.2% instruction delta and −39.5% to −41.6% IPC delta; GEMM
scaled from −20.0% to −25.3% instructions and −22.7% to −29.0% IPC while
cycle delta stayed +3.4% to +5.2%. These are **Observed** under the pinned
simulator configuration.

The trace metadata instruction count is a tracer-side dynamic SASS count; it
is not numerically interchangeable with `gpu_tot_sim_insn`, which includes
the simulator's own warp/instruction accounting. The global read/write totals
matched between modes for the non-atomic rows, so the large GEMV/GEMM gap is
not explained by a different high-level memory footprint.

## Failure and interpretation

The first binary was built with CUDA 12.8 `-lineinfo`. PTX mode failed during
registration on `.loc ... function_name ..., inlined_at ...` and aborted in
`add_ptxinfo`; this is classified as a **baseline parser compatibility
failure**, not a SASS/PTX workload result. Removing `-lineinfo` and rebuilding
made all 12 PTX cases pass. The experiment therefore records the required
CUDA-12.8 compatibility condition (`TRACE_LINEINFO=0` and no compile-time
`-lineinfo`) explicitly.

The PTX wrapper's nonzero shell status is a Slurm-template artifact, not a
simulator failure. Native CUDA event times and PTX replay `kernel_ms` values
are not compared: the former is hardware launch timing and the latter is
simulated/quantized time.

## Conclusion and next step

**Observed conclusion:** SASS and PTX frontends are not interchangeable even
for small single-GPU SM80 kernels. Cycles stayed within roughly ±6% for GEMV
and GEMM, but PTX retired-instruction and IPC accounting differed by about
20–42%; memory/branch microcases showed sign changes up to roughly 49%.
Therefore PTX is suitable as the design path, while SASS remains necessary as
the compiler/hardware validation path. Do not calibrate PTX absolute numbers
to A800 from this experiment alone.

Next, add a second compiler-shape matrix (tiling/unrolling and cuBLAS-sized
but still bounded GEMM) and inspect per-source-line PTX instruction statistics
before changing the simulator core. Multi-GPU behavior remains out of scope.
