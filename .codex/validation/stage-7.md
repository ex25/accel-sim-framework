# 阶段 7 验收：九例完整输出与性能

状态：九例均未运行模拟验收。[实现/集成方案](../plans/stage-7.md)；[公共规则](README.md)；[完整性能口径和基线](../hopper-validation.md#性能比较的口径)。

## 正式运行前需要什么

阶段0～6当前消费者的必要检查有记录，首次联测和完整双缓冲通过；完整110模块能加载，原启动器能取得编码入口并按实际cluster/shared参数启动。不得用no-op、host直接计算专家输出或SASS trace替代PTX执行。

先对原模块16的FC1/FC2合法调用分别检查输出。没有中间golden时，用该次输入做独立CPU分块参考，或人工可计算输入检查；明确哪些是微测、哪些是冻结尺寸。首个有代表性尺寸的专家调用就记录墙钟/RSS并更新预算，不等全部九例跑完。

## 正式命令

按[概览中的环境配置](../hopper-validation.md#执行命令与记录位置)构建并设置PTX周期模式。以下从项目根目录的 `workloads/moe/` 执行，是后续命令，本轮未运行：

```bash
mkdir -p runs
/usr/bin/time -v -o runs/qwen64-128.time.txt \
  python3 run.py --case qwen64 --tokens 128 --mode sim \
  --run-dir runs/qwen64-128
python3 compare.py artifacts/cases/qwen64-t128 runs/qwen64-128
```

后续用对应case/tokens和独立输出目录。保持原二进制与输入hash、一次无预热前向。关闭 `MOE_TRACE_LAUNCHES` 及额外同步/中间抓取；准确配置、构建方式及日志随报告保存。

## 数值与同步通过条件

- `compare.py` 对所有输出检查有限值及既定逐元素容差；同时保存逐位一致、失败元素数、最大绝对误差、相对L2。20%不用于数值。
- 整数路由/计数问题回到阶段1，地址/搬运回到阶段3/5，矩阵布局/累加回到阶段6。发现完整输出不符时先定位首次分歧，不一边调性能一边忽略数值错误。
- 必要组合证据来自前面联测和本阶段真实调用：输入完成后消费、合法复用shared、三类组等待互不混淆、内核退出没有漏写回。无需给九例全程保存逐字节日志。

## 时间比较和校准

按launch index、entry、grid/block/shared匹配同一调用。FC1与FC2即使entry相同也分列。模拟端kernel起止周期转换为时间，排除纯launch/主机空档；ncu比较同批kernel和及主要调用，三个4096再看nsys。原始参考值、采集条件和频率计算保留在概览，不在本文件抄另一份基线。

依次检查：math ops是否少算/重复及tile padding；DRAM/L2字节和组播是否合理；等待是否提前或强制串行；最后才调整能解释差额的延迟/吞吐。改变共用参数后重验受影响调用，不按单个模型/尺寸设置凑数系数。

每例记录：kernel总和、FC1/FC2/gating各自有符号误差，另外关注占比≥5%或能解释主要差额的调用。ROI、DMA和主机间隙分开说明。没有自然运行完整设备时间的用例不填“DMA实测为0”。

## 墙钟与停止条件

按公共规则分列初始化、模拟、比较时间和峰值RSS；用代表性真实专家与完整4096样本更新剩余预算。若模拟速度实际阻塞交付，先定位证据再优化，不扩大成通用模拟器性能项目。

九例数值全部通过，主要异步行为有证据，kernel总和与主要调用接近约20%目标且没有被总和抵消的大偏差，即停止精调。小幅超限、低影响近似写明触发条件/影响/暂缓理由；明显未解释差额不能写成“支持完成”。
