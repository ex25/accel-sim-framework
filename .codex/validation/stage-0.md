# 阶段 0 验收：检查加载、参数与每次启动是否一致

状态：未构建、未运行；下文是未来执行要求，不是通过报告。配套：[阶段 0 实现方案](../plans/stage-0.md)。

## 本阶段通过意味着什么

一个独立测试程序能使用模拟器的CUDA运行时库，启动两份小型PTX模块，传对参数和动态shared请求，得到精确输出及有效设备周期。它证明后续指令测试的入口可用，不证明冻结九例或专家GEMM已经可以运行。

测试按下列顺序推进。遇到失败，报告具体输入、实际结果和首次不符的位置；不靠退出码0、解析成功或日志里出现“launch”判断通过。

| 顺序 | 检查什么 | 能发现的当前问题 |
| --- | --- | --- |
| 1 | 构建、加载库和周期模式 | 程序实际链接真实CUDA库，或只做功能执行却当作周期模型 |
| 2 | sm_90/sm_90a目标传递 | 提取后a后缀丢失，ptxas未处理原目标 |
| 3 | 64B对齐和完整参数字节 | 合法声明被拒绝，或主机写入与内核读取偏移不一致 |
| 4 | 直接API与编译器启动交替 | 配置未建立、Pop未回填、重复压栈或残留旧配置 |
| 5 | 两次不同动态shared请求 | 许可上限被误当实际分配、资源计入/归还使用旧值 |
| 6 | 外部声明及实际失败分支 | 正常程序被声明挡住，或真实失败被当成功继续 |
| 7 | 两模块A→B→A组合 | entry、global/constant或资源信息错误归属 |

### 每次最少保留的记录

保存测试名、输入/预期、源码和提交、编译运行命令、工具链版本、实际库路径、配置文件及散列、输出差异、设备周期。`/usr/bin/time -v` 保存本机墙钟与峰值RSS；装载/初始化结束和kernel执行区间分别记主机时间戳，避免把慢加载误认为慢模拟。

## 3. 参数：分别检查对齐间隙和1344字节完整传递

**对应实现：[参数大小与对齐](../plans/stage-0.md#parameters)。**

对齐规定参数从哪里开始，大小规定要复制多少字节。只测一个位于偏移0的对象，无法证明参数之间的间隙正确；只测小参数，也无法证明真实1344B对象完整，因此保留下面两个小测试。

### 测试一：混合参数的偏移

使用计划中的四参数声明：u32 head、align64的b8 payload[128]、u64 tail、u64 output。输入固定为：

| 参数 | 主机准备的值 | 正确大小/目的偏移 |
| --- | --- | --- |
| head | `0x13579bdf` | 4B / 0 |
| payload | 第i字节为 `(7*i+3) % 256`，i=0..127 | 128B / 64 |
| tail | `0x0123456789abcdef` | 8B / 192 |
| output | 指向已分配输出缓冲区的模拟设备指针 | 8B / 200 |

host用四个独立变量或字节数组保存这些值，再构造 `args[]`，不要先用一个C++结构体自行拼出整个参数区。内核按各参数符号读取head、全部128字节和tail，将它们写到output。

需要同时检查两类证据：

1. `get_param_config` 返回 `(4,0)、(128,64)、(8,192)、(8,200)`；`finalize` 后参数符号使用同样偏移。可用组件检查或测试调试输出读取这些内部状态，不增加生产自动修正逻辑。
2. 设备写回的head、128个字节及tail与表中值逐项一致，output指针确实指向主机传入的缓冲区。

同时检查状态和输出，是为了排除“写入和读取恰好使用了同一种错误偏移，表面结果仍一致”。预期偏移由上表固定，不能再次调用被测布局函数生成预期。

### 测试二：真实参数对象的大小与内部偏移

独立测试entry采用专家代码的参数声明形式：`.param .align 64 .b8 ...[1344]`，另加测试专用输出指针。它只复制参数字节，不执行专家算法，也不修改原专家PTX。

主机填充1344个可预测字节，例如同样的 `(7*i+3) % 256`。内核用已有 `ld.param` 和普通store回写全部1344B，主机逐字节比较；单独展示偏移0、63、64、127、128、1128、1136、1240、1343处的检查结果，覆盖对齐边界、真实字段位置和末尾。

通过条件是完整内容一致、声明大小被记录为1344B、对齐为64B。不能以“复制了64字节”通过，也不要求本阶段理解这段对象中的tensor map语义。

**覆盖指令：**参数声明、`ld.param`、普通地址运算和store；`get_param_config`/`finalize`共同接受同一布局。未使用的设备端子内核参数路径、PTXPlus参数复制、任意非法对齐不扩测。

## 4. 启动：交替调用两种入口，检查配置没有串用

**对应实现：[配置来源与Push/Pop约定](../plans/stage-0.md#launch)。**

准备一个可以回写grid/block、线程索引和输入标记的简单内核，同一个进程依次调用：

| 调用 | 入口 | grid / block | 输入标记 | 预期参与线程数 |
| --- | --- | --- | --- | ---: |
| 第一次 | 直接 `cudaLaunchKernel` | 2 / 32 | 11 | 64 |
| 第二次 | 编译器 `<<<>>>` | 3 / 64 | 22 | 192 |
| 第三次 | 直接 `cudaLaunchKernel` | 1 / 32 | 33 | 32 |
| 第四次 | 编译器 `<<<>>>` | 4 / 32 | 44 | 128 |

先使用动态shared=0和默认stream，隔离启动配置问题。每次输出使用单独缓冲区，精确核对参与线程数、各线程报告的grid/block、标记与线程编号；不能仅核对总输出文件存在。

保存本机编译器生成的host包装调用片段，确认Push→Pop→直接API的实际顺序。测试观察栈深度：每次提交结束恢复调用前深度；Pop的四个输出均等于本次Push的值。调试观察放在测试/已有debug输出中，不加新的公共CUDA接口。

再选一次使用非默认stream的合法启动，核对kernel入队的stream身份，并在**同一个stream**里做输入复制→kernel→输出复制→同步，确认得到该次标记。它只检查stream参数没有丢失，不扩多stream并发/竞争测试。

通过条件是四次都正确、没有残留或重复配置，默认和指定stream都接入已有队列。不能用每次启动前强制清栈或忽略显式参数来修测试。

## 5. 动态shared：检查本次大小、数据及资源占用/归还

**对应实现：[许可上限与实际分配](../plans/stage-0.md#shared)。**

对同一个测试函数设置动态shared许可上限65536B，随后分别以32768B、65536B、32768B启动。数据测试使用合法shared地址：由一个线程写首端和末端4B标记，执行 `bar.sync` 后由同CTA另一线程读取并写回。第三次再次用较小申请，确认函数没有记住第二次的大请求。

### 数据和配置通过条件

- 三次 `kernel_info_t` 保存的动态字节分别为32768、65536、32768，函数许可上限保持65536。
- 各自首尾标记正确，末端访问在本次合法范围内；不靠故意越界探测大小。
- `function_info` 中原有ptxas资源基数未被累加修改；第二次启动不会改变前一次执行对象的值。
- 如果测试模块带少量固定shared标记，再核对它与动态区的标记互不覆盖；不为此展开任意共享符号排列测试。

### 资源和时间模型通过条件

shared功能存储按页保存，写出正确数据还不能证明资源限制正确。另记录如下计算链：

```text
+本次动态字节
+已有ptxas资源基数
=本次每CTA shared占用
      ↓
最大驻留CTA数、L1/shared划分、实际资源占用与归还
```

将基数记为B，SM容量记为S，本次动态请求记为D；shared对驻留数量的限制应为 `floor(S/(B+D))`，最终还需与线程、寄存器及CTA数量上限取最小值。用真实记录的B/S计算预期，不能把B一概当0，也不能重复添加已在B里的system部分。

可使用从H100配置复制出的**单SM测试配置**，保留其容量、寄存器和其它时序参数，只将执行规模缩小。准备足够多CTA，使grid数量不成为驻留限制；选择较少线程/寄存器的测试内核，让shared成为限制因素。报告中列出所有配置差异，不把该测试周期当九例H100性能数据。

检查较大D导致相应驻留限制变化；`max_cta`和适用的实际占用/归还路径采用同一数值。若某个资源分支在当前运行配置不经过，用针对同一函数的组件调用检查公式和增减，不宣称它已有运行覆盖。三次launch完成后资源计数恢复，不能遗留第二次的占用。

大于96KiB的地址、132SM范围、216064B专家总占用留给阶段3；本阶段不因为没有运行大专家就跳过32/64KiB这条动态传递链。

### 受影响SASS回归

本项修改了共用资源函数，因此检查SASS构造的kernel对象新增动态值为0时，原有资源结果不变。有现成小trace则运行相应回归；否则记录组件证据和未运行的trace覆盖，不为本阶段去采集大规模新trace。

## 6. 外部声明和失败出口：区分声明存在与失败被执行

**对应实现：[noreturn与失败调用](../plans/stage-0.md#declarations)。**

使用冻结PTX中的五参数 `__assertfail` 声明及其 `.noreturn` 后缀。准备同一最小程序的正常/失败两条确定路径，分别在独立进程执行：

- 正常路径不调用失败函数，写回固定标记123。预期声明可解析、内核执行完成、输出为123。
- 失败路径确实执行 `call __assertfail`。预期日志明确指出失败位置，进程非零或以失败信号终止，不能继续写出成功标记。
- 另一个最小程序确实执行 `trap`，检查现有报错终止行为；它用于确认已有失败出口，而不是要求重写trap或精调其周期。

这些检查覆盖当前材料中的两个失败分支，不扩任意异常输入、字符串错误处理或恢复重试。测试入口必须区分“预期失败测试通过”和“被测程序成功退出”。

## 7. 多模块组合：证明实际找到了各自的代码和数据

**对应实现：[模块映射](../plans/stage-0.md#modules)。**

同一host测试程序嵌入两个独立fatbinary，而不是只在同一PTX里放两个函数。A有入口 `write_a` 和唯一命名的global/constant数据，B有入口 `write_b` 和另一组唯一名称的数据。两边数据分别能组合出11和22。

通过正常注册接口登记A、B后，按A→B→A启动，分别写到三个输出位置。主机期望为 `[11, 22, 11]`。这个测试可以复用前面目标测试的模块，不必另建第二套加载器。

除输出外，还记录每次host函数标记解析到的entry及资源信息。为使资源归属错误可观察，两模块使用不同的固定shared声明；把各entry的ptxas报告与其 `function_info` 资源值逐项比较。不要假设编译器一定给出不同寄存器数，用实际报告作预期。

通过后保留现有共享符号表即可。失败则报告首次发生的是找不到entry、读错global/constant，还是资源记录串用，再修对应映射；不能据“名称都是default”直接要求全部模块隔离重构。未使用的同名符号跨模块链接不在本次验收范围。

## 进入阶段1的条件

上面七项有明确结果，必要数据复制/同步正确；修改的共用资源路径有对应回归证据。测试运行入口可重复加载单个指定模块，能够输出参数、配置、数值、周期及墙钟记录。

后续真实单模块测试仍要遵守原entry参数布局及固定维度，不能任意缩小缓冲区。完成这些条件后推进，不补完整CUDA ABI、所有非法输入、任意stream并发或DMA精确时序测试。
